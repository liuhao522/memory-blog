# 秒杀系统设计全解：从 Redis+Lua 到消息队列的完整方案

## 背景

在"优选生活"服务平台中，我们实现了优惠券秒杀功能。典型场景是：1元购、满减券，库存 100 张，同一时刻数千人同时抢购。秒杀系统的核心挑战有三个：**防止超卖**、**一人一单**、**高并发下用户响应快且数据库不崩**。

## 整体秒杀流程

秒杀开始前，将优惠券库存提前加载到 Redis；店铺信息、优惠规则等高频读取数据放入 Caffeine 本地缓存。

1. 用户在前端点击**秒杀**
2. 后端在 Redis 里判断库存是否充足
3. 判断该用户是否已经买过（一人一单）
4. **Lua 脚本**原子执行：判断库存 > 0 + 判断用户 ID 是否已存在 → 库存减 1 并记录用户
5. 校验通过，扣减 Redis 库存，通知用户"抢券成功，订单处理中"
6. 发送消息到 **Redis Stream 消息队列**
7. 后端异步消费者：扣减 MySQL 库存 → 创建订单

## 为什么用 Redis + Lua，不用数据库？

| 方案 | 问题 | 结论 |
|------|------|------|
| MySQL 直接扣库存 | 高并发下锁表/行锁竞争，几百上千请求直接打崩 | ❌ |
| `synchronized` / `ReentrantLock` | 只能管单个 JVM，多实例部署完全无效 | ❌ |
| Redis 分布式锁 | 可以跨实例，但加锁-判断-扣减-解锁不是原子的 | 🟡 |
| **Redis + Lua 脚本** | 脚本在 Redis 单线程中执行，天然原子性，性能极高 | ✅ |

Lua 脚本保证原子性，不用分布式锁也能安全扣库存。性能比 `synchronized`、分布式锁高得多。

```lua
-- 秒杀扣库存 Lua 脚本
local voucherId = KEYS[1]
local userId = KEYS[2]

local stockKey = 'seckill:stock:' .. voucherId
local orderKey = 'seckill:order:' .. voucherId

-- 判断库存
if tonumber(redis.call('get', stockKey) or 0) <= 0 then
    return -1  -- 库存不足
end

-- 判断是否已购买
if redis.call('sismember', orderKey, userId) == 1 then
    return -2  -- 已购买
end

-- 扣库存 + 记录用户
redis.call('decr', stockKey)
redis.call('sadd', orderKey, userId)
return 0  -- 成功
```

## 为什么要异步下单？

如果同步直接写 MySQL：

- 高并发几百上千人同时抢，数据库瞬间被大量写入卡死
- 即使不宕机，用户在前端等待时间也极长（MySQL 读写远慢于 Redis 内存操作）

秒杀只需要"抢资格"，不需要立刻写数据库。用消息队列**异步错峰**写入：

- 前端只需知道"在排队中"就证明抢到了
- 后台慢慢消费创建订单，系统压力极小

我们使用的是 **Redis Stream** 做消息队列，异步处理订单入库和库存扣减。

## 高并发优化：多级缓存架构

### Caffeine 本地缓存 vs Redis 缓存

| 维度 | Redis | Caffeine |
|------|-------|----------|
| 类型 | 集中式缓存（所有实例共享） | 本地缓存（每个实例一份） |
| 一致性 | 修改后所有实例立即看到 | 修改后无法同步到其他实例 |
| 适用场景 | 频繁读写、需跨实例共享 | 高频读取、改动极少的配置数据 |

**实践：** 活动信息、优惠券规则放入 Caffeine 本地缓存，库存、用户购买记录放 Redis。

### 多维度限流

- **IP 限流**：同一 IP 1 秒最多 5 次请求
- **用户限流**：同一登录用户 1 秒最多 5 次请求
- **全局限流**：一秒最多处理 2000 次请求

### 缓存穿透/击穿/雪崩防护

| 问题 | 策略 |
|------|------|
| **缓存穿透**（查不存在的数据） | 布隆过滤器拦截无效查询 + 缓存空对象兜底 |
| **缓存击穿**（热点key过期） | 逻辑过期 + 互斥锁 |
| **缓存雪崩**（大量key同时过期） | 动态 TTL 机制 |

### 库存最终一致性保证

- Redis 扣的是"资格"
- MySQL 真正扣减
- Redis Stream 保证至少消费一次
- 极端情况用定时任务校对

## 锁的"作战地图"全景

| 战场 | 锁类型 | 核心作用 | 比喻 |
|------|--------|----------|------|
| **Java层** | `synchronized` | 保证代码块原子性 | 厕所单间：一次只进一人 |
| | `ReentrantLock` | 更灵活，可中断、限时 | 高级厕所：带倒计时 |
| | `ReentrantReadWriteLock` | 读写分离，读读不互斥 | 图书馆 |
| **MySQL层** | 行锁 | InnoDB锁住某一行 | 占座位 |
| | 间隙锁 | 防止幻读 | 画圈圈堵门缝 |
| | 乐观锁（version字段） | 假设没人抢，提交时检查 | 先干再说 |
| **分布式层** | Redis分布式锁 | 跨JVM互斥 | 拿号机 |
| | Lua脚本 | 原子化复合操作 | 一站式柜台 |

## 经验总结

- **秒杀抢的是资格，不是数据持久化**——用 Redis 做前置校验，异步写数据库
- **Lua 脚本是 Redis 的最强武器**——多个操作原子化执行，比分布式锁更简洁
- **缓存策略要组合使用**——穿透/击穿/雪崩各有对应方案，不能一把梭
- **异步削峰是高并发的核心思想**——消息队列不是为了异步而异步，是为了保护数据库
